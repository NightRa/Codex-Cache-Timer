# Windows 11 taskbar-gap overlay research

Research date: 2026-09-25. Scope: the always-visible timer in the gap immediately left of the hidden-icons chevron on this Windows 11 taskbar.

## What Windows supports

| Mechanism | What it promises | Fit for the requested gap |
| --- | --- | --- |
| A topmost popup window | `HWND_TOPMOST` keeps a window above **non-topmost** windows after deactivation. Windows can reorder windows within the topmost group, including on activation. [SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos), [Window Features](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features) | A reasonable overlay, but no absolute position in the topmost group. |
| An owned popup | An owned popup stays above its owner. A top-level owner can be supplied at creation; `GWLP_HWNDPARENT` changes the owner of a top-level window. [Window Features](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features), [SetWindowLongPtr](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowlongptrw) | Helps keep the timer with the taskbar, but does not reserve pixels inside the taskbar or outrank every other topmost window. |
| `WS_EX_TOOLWINDOW` | Keeps a tool window out of the taskbar and Alt+Tab. [Extended Window Styles](https://learn.microsoft.com/en-us/windows/win32/winmsg/extended-window-styles) | Correct for the timer and popup. |
| Notification icon | `Shell_NotifyIcon` adds an icon to the notification area, with tooltip and click callbacks. [The Taskbar](https://learn.microsoft.com/en-us/windows/win32/shell/taskbar) | Supported, but its placement is on the other side of the chevron and is controlled by the user and shell. It cannot provide the requested text slot. |
| Appbar | `SHAppBarMessage` registers a separate application desktop toolbar and negotiates a screen-edge rectangle that does not interfere with the taskbar. [Using Application Desktop Toolbars](https://learn.microsoft.com/en-us/windows/win32/shell/application-desktop-toolbars) | Not a way to occupy the gap *inside* the existing taskbar; it would reserve another strip or screen area. |
| Windows widget | Third-party widgets render in the Windows 11 Widgets Board, which opens from the taskbar. [Widgets overview](https://learn.microsoft.com/en-us/windows/apps/design/widgets) | Not an inline taskbar timer. |

Microsoft's current [Windows 11 taskbar configuration](https://learn.microsoft.com/en-us/windows/configuration/customize-taskbar-windows-11) describes pins, running apps, widgets, and the system tray. The older [deskband documentation](https://learn.microsoft.com/en-us/windows/win32/shell/band-objects) describes a Toolbars menu and taskbar-hosted bands, but it is written for the older taskbar; it does not establish support for a custom Windows 11 gap element. **Inference:** there is no documented API that grants a third-party app an exclusive, always-visible text slot at this exact coordinate. This does not prove no private shell mechanism exists.

## What the live diagnostic shows

`src/CacheTimer/TaskbarOverlayForm.cs` creates a borderless `WS_EX_TOOLWINDOW | WS_EX_TOPMOST` form, assigns the `Shell_TrayWnd` handle as owner, and uses UI Automation to place it left of the chevron. The log at `%LOCALAPPDATA%\CodexCacheTimer\logs\cache-timer-2026-09-25.log` confirms `GetWindow(GW_OWNER)` equals the taskbar handle, `IsWindowVisible` stays true, and painting continues while the timer vanishes. At 21:38 local, `WindowFromPoint` first hit Snipping Tool's `XamlWindow`, then hit `Shell_TrayWnd`; it later recovered when the chevron coordinate moved back. This is an **occlusion / shell transition**, not a timer-state or painting failure. The exact Explorer implementation behind the latter hit is not established by the log.

The Snipping Tool hit is expected: another topmost UI can cover an ordinary topmost overlay. Reasserting the timer above an active capture surface would fight the user's current UI. The `Shell_TrayWnd` hit while ownership is reported is more surprising. The owner rule describes window Z order, but the observed taskbar rendering/hit-testing does not maintain visibility at every point of the shell's transition. We should use the observation as a compatibility limit, not assert an undocumented explanation about Windows 11's internal XAML surfaces.

The current form sometimes calls `SetWindowPos(HWND_TOPMOST)` after movement and when `WindowFromPoint` detects that the taskbar covers it. [SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos) is the documented way to change Z order, but a subsequent shell or app action can reorder it again. No documented flag makes a third-party window permanently outrank all other topmost UI. Microsoft's [window-management guidance](https://learn.microsoft.com/en-us/windows/win32/uxguide/win-window-mgt) also advises respecting the user's window order.

## Approaches to avoid

- **`SetParent` into Explorer.** This makes the timer a child of a window owned by another process, rather than an owned popup. Microsoft documents cross-process DPI-awareness resets or unexpected behavior, plus the need to manage `WS_CHILD`/`WS_POPUP` styles manually. It does not create a supported taskbar extension. [SetParent](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setparent)
- **Continuous `SetWindowPos` or z-order polling.** It can reduce an occlusion interval but cannot guarantee zero flicker, and it may cover user-initiated overlays. `HWND_TOPMOST` itself is a group, not an exclusive layer. [SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos)
- **Treating appbars or widgets as inline taskbar plugins.** Their documented placement is outside that slot. [Appbars](https://learn.microsoft.com/en-us/windows/win32/shell/application-desktop-toolbars), [Widgets](https://learn.microsoft.com/en-us/windows/apps/design/widgets)

## Practical recommendation

1. Keep a single taskbar-owned, non-activating tool-window popup for this exact-gap placement. Establish its owner and styles at creation, and verify the native owner, `WS_EX_TOPMOST`, rect, and hit-test state in logs. Reacquire the taskbar after Explorer restarts; the shell broadcasts `TaskbarCreated` to top-level windows for that case. [The Taskbar](https://learn.microsoft.com/en-us/windows/win32/shell/taskbar)
2. Reposition on actual shell/layout changes, not every second. `SetWinEventHook` can receive out-of-context window events without injecting code; `EVENT_OBJECT_LOCATIONCHANGE` covers top-level window movement and `EVENT_OBJECT_REORDER` covers child-order changes. These are useful triggers to **check** geometry/hit tests, but Microsoft recommends verifying which events a particular UI element emits. An event hook is a cleaner way to react; it is not a visibility guarantee. [SetWinEventHook](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwineventhook), [Event Constants](https://learn.microsoft.com/en-us/windows/win32/winauto/event-constants)
3. Do not raise the timer over Snipping Tool, menus, or other intentional foreground overlays. If Explorer alone occludes the timer after its transition, a single delayed, conditional `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE | SWP_NOMOVE | SWP_NOSIZE)` is reasonable, with logging. This is a mitigation, not a documented absolute guarantee. [SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos)
4. Be candid about the limit: the exact gap cannot currently be guaranteed with a supported Windows API. If uninterrupted visibility is a hard requirement, a notification icon is the supported taskbar-integrated option, though it would change the chosen placement. [The Taskbar](https://learn.microsoft.com/en-us/windows/win32/shell/taskbar)

## Further diagnosis worth doing before changing the window model

At the moment of an Explorer-only occlusion, log the **full hit HWND chain** (hit HWND, class, root, owner/parent, process ID and styles), plus the overlay's preceding and following Z-order neighbors (`GetWindow` with `GW_HWNDPREV` / `GW_HWNDNEXT`). Compare those values before and after the chevron moves. `WindowFromPoint` and `GetAncestor(GA_ROOT)` alone identify the hit surface and root but do not explain *why* Explorer won the composite at that point. [GetAncestor](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getancestor), [Window Features](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features)
